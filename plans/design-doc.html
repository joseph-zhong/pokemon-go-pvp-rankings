01 — The problem

It looks like a database problem. It isn't.

stadiumgaming.gg's rank checker — and every clone like it — reads as a lookup-table product, but underneath it's a small, deterministic calculation over a Pokémon's base stats. The reason these sites feel heavy is ads and bloat sitting on top of that calculation, not the calculation itself.

So the real goal isn't "clone the table." It's: run the same 4,096-way sort in the browser, with nothing in the critical path except math.

02 — The algorithm

How the ranking is actually calculated

A Pokémon's real stat at level L comes from three fixed base stats (Attack, Defense, HP) and a CP Multiplier — a table Niantic defines once per half-level, from 1 to 51.

atk(IV_a, L) = (baseAtk + IV_a) * CPM(L)
def(IV_d, L) = (baseDef + IV_d) * CPM(L)
hp (IV_h, L) = floor((baseHP + IV_h) * CPM(L))

CP(L)          = floor( atk * sqrt(def) * sqrt(hp) / 10 )
statProduct(L) = atk * def * hp        // linear — no sqrt. This is what ranking sorts by.

The rank-checker algorithm, per Pokémon per league

for each of the 4096 (IV_a, IV_d, IV_h) combos in 0..15:
    walk L down from 51.0 in 0.5 steps until CP(L) <= league cap
    record statProduct at that L

sort all 4096 results by statProduct, descending
    (ties: higher Attack stat, then higher HP stat, then higher CP, then higher HP IV)

rank       = 1-indexed position of the combo you asked about
percentage = statProduct / statProduct(best combo) * 100

No league ever stores 4,096 rows per Pokémon anywhere — it's recomputed on demand. 4,096 iterations of arithmetic is sub-millisecond in JS, even on a low-end phone.

The counterintuitive part, worth surfacing in the UI: Attack enters the CP formula linearly, but Defense and HP sit under a square root. A lower Attack IV lets a Pokémon reach a higher level before hitting the CP cap, and every stat benefits from that level's higher CPM. That's why "low attack, high bulk" spreads often outrank 15/15/15 in Great and Ultra League — and why Master League, which has no CP cap, is the one place 15/15/15 is simply best: the level-cap trade-off disappears entirely.

03 — Source of truth

Where the data comes from, and how it stays current

Base stats and move data ultimately live in Niantic's GAME_MASTER file, shipped as a protobuf inside the game client. Nobody sane parses that directly for a hobby project.

In practice, the whole PvP tooling ecosystem — PvPoke, and almost certainly stadiumgaming.gg downstream of it — treats pvpoke/pvpoke's gamemaster.json as the de facto source of truth: MIT licensed, maintained by an active community within hours to days of any game update, already normalized into sane JSON.

Recommendation: don't re-derive this data ourselves. Pull PvPoke's gamemaster.json on a schedule, slim it to just what a rank checker needs (species id, name, base stats, forms, release status — drop move data entirely), and commit the slim file as a build input.

What changesHow oftenHow we catch it
New Pokémon / formsWeekly-ish, more during eventsScheduled fetch diff
Base stat correctionsA few times a yearScheduled fetch diff
CP Multiplier tableOnly on a level-cap raise (~3× ever)Manual — flagged in code
League caps / cup rulesRare, GBL season changesManual review

A daily GitHub Action that fetches the upstream file, regenerates our slim data file, and opens a PR is enough. Cloudflare Pages redeploys on merge.

04 — Architecture

No backend, no database, no ad network

┌────────────────────────┤ GitHub Action │ pvpoke/pvpoke │ (daily cron) ───┊ gamemaster.json (MIT) │ │ └────────────────────────┮ ▼ scripts/fetch-gamemaster.ts (slims to {speciesId, name, baseStats, forms, tags}) │ ▼ data/pokemon.min.json ──┊ committed ──┊ Cloudflare Pages build │ ▼ static HTML/JS at the edge all ranking math runs in-browser
  • Frontend: plain TypeScript + Vite. No React/Vue — the app is one form and one result panel; a framework adds bundle weight for no real benefit here.
  • Calc module: pure functions, zero DOM dependency, fully unit-testable.
  • Data file: one JSON blob, ~200–400KB gzipped, fetched once, cached hard at the edge via a content-hashed filename.
  • Hosting: Cloudflare Pages, static build, free tier covers this comfortably.
05 — MVP scope

One page, three inputs, instant output

Inputs: Pokémon search (typeahead over the local data file), league selector (Great / Ultra / Master, optionally a custom CP cap for special cups), and three IV fields — Attack, Defense, HP, 0–15 each.

Outputs, live on every keystroke, no submit button, no spinner: best level under the cap and resulting CP, stat product and percentage relative to that Pokémon's best combo, and rank out of 4,096. Stretch: show the best IV spread alongside for comparison.

No accounts, no ads, no server-side anything.

06 — IV input UX

Dropdown vs. stepper vs. slider

PatternProsCons
<select> dropdownFamiliar, accessible for freeSlowest: scroll a 16-item list, ×3 fields
SliderVisual, funImprecise on touch, still needs a numeric readout
Number input + stepperType directly, click ▲▼, or arrow-key; fast across 3 fieldsNeeds explicit min/max/step + validation

Recommendation: <input type="number" min="0" max="15" step="1" inputmode="numeric"> styled as a compact stepper, one per stat. Native keyboard support, native mobile numeric keypad, full accessibility, nothing custom to maintain. Save the real <select> for the league picker, where there are only 3–4 options and nothing faster helps.

Nearly-free extras worth building in from day one:

  • URL state — ?pokemon=azumarill&league=great&ivs=0-15-14, so results are shareable and the back button works, with zero backend.
  • Paste support — accept 12/14/15-style strings pasted into any field and auto-split, matching common IV-screenshot formats.
  • No debounce — the computation is sub-millisecond, so update on every keystroke instead of adding artificial lag.

10 — Top 5 & nearby ranks

Context beyond a single number

stadiumgaming.gg shows a top-10 list alongside the single rank — useful context that a bare "#26 / 4096" doesn't give you. This is free to add: rankIvs already builds and sorts the full 4,096-combo array internally to find one rank, then throws the rest away. Exposing that array instead of discarding it costs nothing extra.

API change: replace the single-result rankIvs with rankAllIvs(base, league, levelCap), returning all 4,096 combos sorted and ranked. A findCombo(all, ivs) helper looks up one entry by IVs. This becomes the one source of truth for the query result, the top-5 list, the nearby list, and the rank slider below (§11) — computed once per species/league/level-cap, not once per feature.

  • Top 5: all.slice(0, 5).
  • Nearby: a window centered on the query's rank — 5 ranks better and 5 ranks worse (11 rows including the query), clipped at the #1 / #4096 boundary.

Both render as small tables (rank, IVs, level, CP, %), and each row is clickable — clicking loads those IVs into the form. Browsing the leaderboard doubles as a way to explore "what if I had these IVs instead."

11 — Rank → IVs explorer

Reverse lookup, not just forward

The flow so far is one-directional: type IVs, read off a rank. Sometimes the useful question runs the other way — "what IVs would land around rank #50?" Since rankAllIvs returns a rank-sorted array, that reverse lookup is just indexing: all[rank - 1]. No new math, only a new way to read the same table.

UI: a labeled range slider from "Best (#1)" to "Worst (#4096)". Dragging it doesn't open a separate preview — it sets the actual IV fields to whatever combo sits at that rank, the same as typing IVs directly or clicking a Top-5/Nearby row would. One state, three ways to set it, so the rank number, the top-5 list, and the nearby list always stay in sync with whatever's being explored.

Performance: dragging fires many events per second, but it never recomputes the 4,096-combo ranking — that only happens when species, league, or level cap changes. A drag tick is a single array index plus a re-render, comfortably sub-millisecond.
